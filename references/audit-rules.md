# 审查规则细则

六关的 PASS 底线、FAIL 与熔断分界、熔断分级、换角度池、失败模式反查清单、降级矩阵和修复纪律。

## 一、六关判定口径

| 关卡 | PASS 底线 | FAIL | 熔断 |
| :-- | :-- | :-- | :-- |
| 1 需求对齐 | 原始需求逐条都能在产物里找到对应内容 | 漏项、擅自加戏、偷换目标 | — |
| 2 事实核验 | 数据、尺寸、参数、引用、结论均可溯源到明确出处，**且已与出处逐项比对一致**（见下方「2 事实核验 · 比对条款」） | 无法溯源（须降级标注「待核实」或删除）；**或经比对与出处不一致** | 确认无中生有 → 可修复熔断 |
| 3 完整性 | 无占位符残留、无空章节、无断链、文件可正常打开；**结构化文件（.json / .yaml / .yml）语法解析通过** | 空章节、未闭合标签；**结构化文件解析失败** | 残留占位符、文件打不开、**配置文件语法错误** → 可修复熔断 |
| 4 格式与可读性 | 命名规范、单位一致、层级正常、中文表述、手机端可读、无乱码 | 违反其中任一项 | — |
| 5 交付方式 | 落在约定目录；只展示最新且相关的产物 | 落错目录，或混入中间文件与历史版本 | — |
| 6 风险与合规 | 无个人文件操作、无敏感信息、无版权与学术诚信风险 | 存在需人工复核的合规疑点 | 未确认就动个人文件、产物内容用了未经确认的假设或数据 → 硬熔断；含密钥或证件号 → 先就地清除再上报 |

### 2 事实核验 · 比对条款（v1.3.0 新增）

引用外部出处（用户提供的报告截图 / 官方文件 / 公开数据 / 第三方测评结果）时，**必须调取该出处逐项比对**，比对维度至少五项：

| 维度 | 说明 |
| :-- | :-- |
| 数值 | 数字本身是否一致 |
| **排列顺序** | 出处若按特定逻辑排序（类型优先、层级降序等），产物必须照搬，**不得自行重排** |
| **名称与标签** | 术语译法、类型代号（如 R-I-C）是否与出处一致 |
| 单位 | 分制、百分比、倍率口径是否一致 |
| 口径 | 统计范围、时点、样本是否一致 |

**只核数值、不核顺序与标签，是最常见的漏检模式**——顺序与标签本身携带信息，改动顺序等于篡改出处的判断。

比对结果写入关卡 2 的证据列，写法：`《出处名称》↔ 产物：5 项维度逐项一致 / 第 X 项不一致（详见…）`。

## 二、熔断分级

**可修复熔断** —— 自己修，修完重跑全部六关；修不掉就停下上报：

- 虚构数据，或把推测写成结论
- 残留占位符
- 文件无法正常打开
- **配置文件语法错误（.json / .yaml 解析失败）**——这类故障不会自我暴露，只会让依赖它的功能静默失效，必须修完再用脚本复验，不得靠目测放行

**硬熔断** —— 立即停下，不许自行处置，直接上报等用户决定：

- 涉及个人文件操作却未先扫描并取得用户确认
- 产物内容中使用了未经用户确认的假设或数据
- 产物含密钥、证件号等敏感信息（先就地清除，再上报）

硬熔断禁止「先展示后补修」，也禁止以「反正已经修了」为由继续。

## 三、换角度池

连续两次通过必须使用两个不同角度：

1. 按关卡逐项查：从第 1 关走到第 6 关，逐关取证
2. 按内容逐段通读：按产物自身顺序从头读到尾，边读边记疑点
3. 换成读者视角：站在交付对象的立场看——仅自己看能否复现、老师看能否验收、评委看能否答辩
4. 按失败模式反查：拿第五节的清单逐条问「这个产物有没有这个问题」
5. 按改动半径反查（v1.5.0 新增）：列出本轮动过的每个文件，逐个问「它波及的别处同步了没有」——同族副本、版本号与计数、引用方、配置语法

重档必须用上角度 4。不得以「与上轮一致」为由跳过复查。

## 四、证据写法

每条证据必须能在产物里定位到具体位置，写法三选一：

- 章节名 + 原句摘录
- 行号 + 原句摘录
- 命令 + 命令输出

禁止写法：「看起来没问题」「基本正常」「整体良好」「无异常」。无法判断时写「无法判断」并说明缺什么信息，不得默认为 PASS。

## 五、失败模式反查清单

逐条问「这个产物有没有这个问题」：

- 虚构数据：有没有编造的样机、销售数据、文献、测试结果、用户反馈
- 无出处数字：有没有算出来但没写算式的数字、抄来但没标来源的尺寸或参数
- 占位符残留：TODO、xxx、待补、待填、示例文本、空表格、空列表
- 版本混入：有没有把中间文件、历史版本、草稿、副本一并展示
- 目录与命名：产物是否落在约定位置，命名是否符合约定，有没有带多余后缀
- 编码与乱码：中文是否正常，单位符号是否被替换，表格是否错列
- **配置语法**：`.json / .yaml` 改完后是否让脚本真跑过一遍解析；有没有「目测看着对、实际解析失败」的情况（裸引号未转义、尾逗号、Tab 缩进、缩进层级错位）
- 需求漂移：有没有做了用户没要求的事，或漏掉用户要求的事
- 敏感信息：密钥、令牌、证件号、手机号、住址、账号
- 个人文件：有没有移动或删除个人目录里的内容
- **出处一致性**：引用了外部出处的数值 / 结构 / 顺序，是否与出处逐项比对过；有没有「只核数值、不核顺序与标签」的情况
- **改动半径**：本轮改过的文件，其配套项是否逐项核过——同族副本（如两份 `MEMORY.md`、派生的阅读版 HTML）、版本号与计数、索引与目录、引用方、配置语法；有没有「改了 A、B 还是旧的」
- 可复核性：结论、数据、尺寸能否被用户当场验证

## 六、功能降级矩阵

| 情况 | 受影响功能 | 降级做法 | 必须标注 |
| :-- | :-- | :-- | :-- |
| 本机无 Python 或脚本不可执行 | 确定性扫描 | 人工逐项核对同一份检查点 | 「未过确定性扫描」 |
| 本机无 pyyaml | YAML 语法校验 | 只查 Tab 缩进等基础项，语法未完整验证 | 「YAML 未过完整语法校验」 |
| 产物文件不可读或被占用 | 第 3、5 关 | 按上下文中的产物内容审查 | 「未直读文件」 |
| 无法断定交付对象 | 档位判定 | 按常规档处理 | 「交付对象未知」 |
| 产物为对话内产出（未落盘） | 第 1、3、5 关 | 按对话上下文审查；第 5 关改判「是否误展示中间/历史产物」；无文件可扫时标注未过确定性扫描 | 「未落盘，按上下文审查」 |
| 原始需求缺失 | 第 1 关 | 改为检查产物自身是否自洽完整 | 「需求对齐降级」 |
| 某关无法判断 | 该关结论 | 写「无法判断」并说明缺什么信息 | 不得默认 PASS |
| 文件完全无法读取 | 全部 | 停止审查并说明原因 | — |

## 七、修复纪律

- 只修审查范围内的问题，不顺带重构
- 每项修复动作写进自审卡的「修复动作」列
- 修完重跑全部六关，不准只复查改过的关卡
- 不为了分数好看改判等级，不空转一轮凑「连续两次」
- 可修复熔断自己修的，只做消除问题所需的最小改动；无法消除时停下上报，不绕过
